# ПОС - Преподавательская Оценка Студентов

Консольное приложение для учета преподавательской оценки студентов: студенты, рубрикатор критериев, оценки, расчет итога по весам и экспорт итогов в CSV / JSON.

## Технологии

- Java 25, Gradle 9.2 (Gradle Wrapper лежит в проекте);
- Spring Boot - DI-контейнер;
- JUnit 5 - тесты;
- JaCoCo - тестовое покрытие;
- Checkstyle (sun_checks без Javadoc-правил) - проверка кодстайла.

## Запуск

Нужна только JDK 25. Все команды выполняются из папки проекта `hw-02`.

Интерактивное меню:

```bash
./gradlew bootRun --console=plain --quiet
```

То же самое через плагин `application`:

```bash
./gradlew run --console=plain --quiet
```

Сквозной демо-сценарий без ввода (студенты и критерии, оценки, итог, экспорт). Его же можно запустить из меню пунктом `14`.

```bash
./gradlew bootRun --args=--demo --console=plain --quiet
```

Сборка JAR и запуск без Gradle:

```bash
./gradlew bootJar
java -jar build/libs/pos.jar
java -jar build/libs/pos.jar --demo
```

Файлы экспорта сохраняются в папку `results/`, например `results/grades.csv`. Полный путь приложение печатает после экспорта.

## Предметная область

### Ubiquitous Language

| Термин ТЗ  | В коде                | Смысл                                          |
|------------|-----------------------|------------------------------------------------|
| студент    | `Student`             | кого оценивают                                 |
| рубрикатор | `Rubric`              | набор критериев курса                          |
| критерий   | `Criterion`           | за что ставят балл; есть `maxScore` и `Weight` |
| вклад      | `Weight`              | доля критерия в итоге, от 0 до 1               |
| балл       | `Score`               | число в диапазоне критерия                     |
| оценка     | `Evaluation`          | "студенту по критерию поставили балл"          |
| итог       | `FinalGrade`          | результат по 10-балльной шкале                 |
| расчет     | `FinalGradeCalculator` | Domain Service, считает итог                  |

### Инварианты

- балл не выходит за пределы критерия: `0 <= score <= maxScore` - проверяет `Score` при создании, поэтому неверный балл просто нельзя создать (ни при выставлении, ни при исправлении);
- оценку можно выставить только по критерию из рубрикатора - `EvaluationFactory` берет критерий через `rubric.criterion(id)`, который бросает `DomainValidationException`, если критерия нет;
- одна оценка на пару "студент - критерий", повторную нужно исправлять;
- `maxScore > 0`, вес в `(0; 1]`, сумма весов рубрикатора не больше 1, названия критериев уникальны - следит `Rubric`;
- нельзя удалить критерий, по которому уже есть оценки;
- при удалении студента удаляются его оценки;
- итог не хранится, а каждый раз считается по текущим оценкам в `FinalGradeCalculator`. Перед расчетом сервис проверяет, что все оценки принадлежат этому студенту, их критерии есть в рубрикаторе и нет двух оценок на один критерий.

### Формулы итога

`ratio = score / maxScore`

- **Weighted sum** (по умолчанию): `10 * sum(weight * ratio)` по всем оценкам. Неоцененный критерий дает 0 - это накопленная оценка.
- **Current grade**: `10 * sum(weight * ratio) / sum(weight)` только по оцененным критериям - "какая оценка у студента сейчас".

Округление арифметическое: 5.5 округляется до 6, 5.49 до 5.

## Карта DDD

```text
pos.domain
  model        Entity: Student, Criterion, Evaluation
               Aggregate Root: Rubric
               Value Object: Score, Weight, FinalGrade
               EvaluationFactory, DomainChecks
  repository   StudentRepository, RubricRepository, EvaluationRepository
  service      FinalGradeCalculator (Domain Service), GradingStrategy,
               WeightedSumStrategy, CompletedCriteriaStrategy
  exception    DomainValidationException
```

### Entity и Value Object

**Entity** - объект с идентичностью, сравнивается по id и может меняться. `Evaluation` - это Entity: у нее есть `id`, ее можно исправить (`correct`) или отменить, и после исправления это все еще та же самая оценка #5. Два объекта `Evaluation` с одинаковым id равны, даже если балл у них разный. Так же устроены `Student` и `Criterion`.
**Value Object** - неизменяемое значение без идентичности, сравнивается по содержимому. `Score(8, 10)` равен любому другому `Score(8, 10)`. `Score` нельзя изменить: при исправлении оценки создается новый `Score`, и его конструктор снова проверяет диапазон. Остальные VO - `Weight` и `FinalGrade`. Все VO сделаны через `record` с проверкой в конструкторе. Идентификаторы - обычные `int`, их выдают репозитории.

### Агрегаты

- `Rubric` - корень агрегата для `Criterion`. Критерий создается только через `rubric.addCriterion(...)` (конструктор `Criterion` package-private), поэтому правила про сумму весов и уникальные названия нельзя обойти.
- `Student` - отдельный агрегат.
- `Evaluation` - отдельный агрегат, ссылается на студента и критерий по id, а не по ссылке на объект. Оценок много, и держать их внутри студента или рубрикатора было бы неудобно.

### Repository

Интерфейсы репозиториев лежат в домене (`StudentRepository`, `RubricRepository`, `EvaluationRepository`) - это порты. Реализации в `infrastructure.persistence` хранят данные в памяти.

### Domain Service

`FinalGradeCalculator` - правило, которое не принадлежит одной сущности: для итога нужны студент, рубрикатор и все его оценки сразу. Сервис проверяет согласованность данных и считает итог выбранной стратегией.

## Архитектура: Ports and Adapters

```text
pos
  domain             ядро: модель, инварианты, порты-репозитории
  application        фасад, DTO, порт ResultExporter
  infrastructure     адаптеры
    persistence      in-memory репозитории (реализуют порты домена)
    export           CSV / JSON экспорт (реализуют ResultExporter)
    console          консольный UI (входной адаптер)
    config           PosConfiguration - composition root
  PosApplication     запуск Spring Boot
```

```text
infrastructure -> application -> domain
```

- `domain` не зависит ни от чего: в нем нет Spring, файлов и консоли;
- `application` зависит только от `domain` и объявляет свой порт `ResultExporter` - фасад не знает про CSV и JSON;
- `infrastructure` реализует порты и вызывает фасад;
- граф объектов собирается на краю - в `PosConfiguration` и через аннотации адаптеров (`@Repository`, `@Component`).

### DI

DI-контейнер - Spring. Классы домена и приложения не содержат аннотаций Spring, поэтому они регистрируются как бины в `PosConfiguration` (`@Configuration` + `@Bean`). Адаптеры помечены `@Repository` / `@Component` и находятся сканированием. Все зависимости передаются через конструктор. `ConsoleRunner` помечен `@Profile("!test")`, чтобы в `SpringContextTest` не запускалось меню.

## Паттерны GoF

| Группа         | Паттерн         | Где                                         |
|----------------|-----------------|---------------------------------------------|
| порождающий    | Factory         | `EvaluationFactory`                         |
| структурный    | Facade          | `GradingFacade`                             |
| поведенческий  | Strategy        | `GradingStrategy` + 2 реализации            |
| поведенческий  | Template Method | `FileResultExporter`, CSV / JSON            |

**Factory - `EvaluationFactory`.** Боль: оценку можно было бы создать в любом месте, забыв проверить, что критерий есть в рубрикаторе, и взять `maxScore` не того критерия. Конструктор `Evaluation` package-private, поэтому единственный способ создать оценку - фабрика. Она находит критерий в рубрикаторе и строит `Score` с его максимумом. Дату ставит по внедренному `Clock`, поэтому ее легко проверить в тесте.
**Facade - `GradingFacade`.** Боль: каждому пункту меню нужны два-три репозитория, фабрика, калькулятор и стратегия. Без фасада эта логика (проверка повторной оценки, запрет удалять критерий с оценками, каскадное удаление оценок студента) размазалась бы по консоли. Фасад - единая точка сценариев: консоль передает простые числа и строки и получает результат.
**Strategy - `GradingStrategy`.** Боль: правило итога меняется (итоговая накопленная оценка или текущая успеваемость по оцененным критериям), а `FinalGradeCalculator` и проверки согласованности при этом одни и те же. Правило выбирается в меню (пункт 12), новое правило - это новый класс, калькулятор не меняется.
**Template Method - `FileResultExporter`.** Боль: экспорт в любой формат - это одинаковый каркас (открыть файл, заголовок, строки, окончание, закрыть файл в `finally`, превратить `IOException` в `ExportException`). Каркас - `final`-метод `export`, а `CsvResultExporter` и `JsonResultExporter` переопределяют только `writeHeader` / `writeRow` / `writeFooter`.

## Сознательные упрощения

- Хранилище - в памяти. Чтобы сохранять данные в файл, достаточно написать новые адаптеры портов-репозиториев, домен и фасад не меняются.
- Рубрикатор один на курс. Для нескольких курсов `RubricRepository` нужно будет искать рубрикатор по id курса.
- Пересдачи и апелляции не реализованы; исправление оценки сейчас просто меняет балл и комментарий.

- ИИ использовался для разбора ТЗ, обсуждения доменной модели (границы агрегатов, Entity / VO) и выбора уместных паттернов.
- ИИ помог подготовить первоначальную структуру папок и файлов модуля, часть тестов и форматировать описание проекта в README.
- ИИ помог рассмотреть какие паттерны gof уместны и какую проблему решает каждый, а также помог с реализациями внутри проекта.
- ИИ подготовил демо-режим для демонтрации работы программы.

Примеры промптов:
- Изуси ТЗ из файла и как лучше всего структировать такой проект
- Где должны проходить границы агрегатов, нужно ли хранить оценки внутри студента
- Сделай экранирование кавычек и точке с запятой при экспорте CSV
- Какими патернами gof тоит воспользоваться в этом проекте чтобы не было овер использовани и как лучше реализовать структурынй паттерн
- Сделай демо-режим чтобы показать работу программы (--demo без продового меню)

- Сделай вторую стратегию, которая считает итог только по оцененным критериям с нормализацией весов
- Напиши обработку ошибок в главном цикле меню, чтобы при неверном вводе программа не падала

Критическое мышление:

ИИ было предложено написать собственный DI-контейнер, я выбрал Spring. Также предложенная инфра ИИ была упрощена. По умолчанию экспорт было предложено писал файлы прямо в папку проекта - я вынес их в отдельную папку. Я решил закрывать файл вручную в finally, чтобы явно видеть, что происходит при ошибке записи и закрытия.
